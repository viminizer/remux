remux agent harness

Claude and Codex pick GitHub issues on their own, fix their own blockers, decide from real references, and get reviewed by Codex. You only step in when an agent is truly stuck, and you do it from the remux PWA on your phone.

Problem today

  • Agents stop and ask questions.
  • They sit idle most of the time.
  • They stop at blockers instead of fixing them.
  • Subagents use too many tokens.
  • Claude reviews take too long and find too many issues.

Goal

  • Agents find work on their own and finish it.
  • Claude and Codex work together on one queue.
  • Blockers become issues and get fixed.
  • Decisions are based on references, not guesses.
  • Codex reviews, fixes, and closes the loop.
  • You only get pinged when you are really needed.

01The parts

Each part does one job. remux stays thin: it shows state and sends a few commands. It does not run the work itself.

To-do list

GitHub issues

The default tracker for all projects. Labels show the state of each issue and PR.

Worker

Build loop

One loop per agent (Claude, Codex). Takes a ready issue, works in its own worktree, opens a draft PR. One issue per run, then exit.

Worker

Review loop

Codex only. Takes PRs labeled needs-review, fixes real bugs, then merges or hands off.

Shared state

tmux session options

Each loop stores its state on its own tmux session: agent, issue, state, since when, scope, instructions. No extra files.

Per project

Settings file

Lives in the repo. Holds the mode (personal or company), reference projects, and default instructions.

Per project

Decision log

Lives in the repo. One short entry per decision, so later runs stay consistent and do not research the same thing twice.

Your phone

remux (server + PWA)

The server reads state from tmux, like it already does. The PWA shows the loops, sends alerts, and lets you start, stop, and unblock.

02The full flow

Each agent run is short and fresh: one issue, one process, then exit. The loop starts the next one right away, so nothing waits on you.

03Labels are the state

GitHub is the single source of truth. Every step is a label change, so any loop or remux can see where each piece of work is. <scope> is the short name of the loop's instructions, like backend. A loop with no instructions uses full.

04Personal vs company mode

Same flow. Only the last step changes. The mode is set in the project's settings file.

Personal projectCompany project
TrackerGitHubGitHub

Finding the supervisor, first match wins:

  1. CODEOWNERS file in the repo. GitHub asks code owners for review on its own when a draft PR is marked ready, so the loop does nothing.
  2. Git history: whoever reviewed or merged the most recent PRs.
  3. Fallback: joonsung.um.

05Custom instructions

Two layers. The second adds to the first, or replaces it for that session.

Layer 1

Project defaults

Rules that rarely change, in the settings file. Example: "Never touch the payment module."

Layer 2

Session instructions

What you want from this loop now, from the remux start form. Example: "Only do the backend parts of the issues." Comes with a scope name and an add / replace choice.

Each run builds its prompt in this order:

  1. Fixed agent rules (section 09)
  2. Project defaults
  3. Session instructions
  4. The issue itself
Editing while a loop runs: the change is saved to the tmux session and used from the next run. The current run finishes with the old instructions, so no half-done work. Changing the scope name also changes the wip: and done: labels the loop looks at.

06Scoped and partial issues

Partly done

Issue stays open

The PR says "Refs #12", not "Closes #12". The agent comments what it did and what is left, then adds done:<scope>. A full scope loop closes the issue as usual.

Nothing to do

Skip cheaply

If the issue has no work for this scope, the agent adds done:<scope> with a one-line comment and exits. The issue stays ready for other loops.

Later

Two loops, two scopes

Start with one loop per project. Because the claim label includes the scope, a backend loop and a frontend loop can later share one issue without blocking each other. For now you close split issues yourself.

07Blockers

A blocker is a new issue, not a reason to stop. The agent never fixes the blocker inside the same run. The blocker gets its own issue, PR, and review.

Links use GitHub's built-in "blocked by" issue relationships, so the dependency is visible on the issue page.

08How decisions are made

Decide from evidence, not taste. Only for real decisions: data shape, library choice, API design, how to merge two conflicting approaches. Naming a variable is not a decision.

  1. Decision log. Already decided? Follow it.
  2. This codebase. Existing pattern? Use it.
  3. Reference projects. How does project A solve it? Project B? Pick the better one or combine, and say why.
  4. The internet, when there are no references or they do not cover it. Real-world cases: well-known open source, official docs, engineering blog posts.
  5. Senior engineer judgment. 2 or 3 options with tradeoffs, pick one, write down why.
Record

Two places

  • A "Decisions" section in the PR: choice, reason, source.
  • One entry in the decision log in the repo.
Cost

Keep it cheap

  • Research is time-boxed: each reference project once, a few web searches, then decide.
  • Reference projects are local read-only clones on the home machine.
Review

Codex checks it

A PR that goes against the decision log is a real finding.

09Rules the agents follow

  1. Never ask questions. If something is unclear, pick the safest option and write the assumption in the PR.
  2. A blocker is a new issue, not a reason to stop. Only things code cannot fix go to needs-human.
  3. When stuck, ask one short question, with 2 or 3 options when possible. It will be read on a phone.
  4. One issue per run, in its own worktree. Exit when done. No long sessions, no subagents.
  5. Stay inside the session instructions and scope.
  6. Make real decisions from the decision log, codebase, references, then the internet. Record them.
  7. Review fixes only real bugs. Ignore style and small things.
  8. One review pass only. If tests still fail after fixes, mark needs-human. No endless fix loops.
  9. Nothing merges unless tests pass. In company mode, nothing merges at all.

10remux PWA (mobile first)

Everything is managed from the phone. Main rule: tap, don't type. Each loop runs in its own named tmux session (loop-claude, loop-codex, loop-review). The server reads their state from tmux and sends pushes. Nothing new sits in between.

Answering a stuck agent, the most common action:

  1. The push opens straight to that issue.
  2. The agent's short question is at the top, with option buttons when possible.
  3. Tap an option or type a short reply, then tap Send and resume. It posts the comment and sets ready.
Alerts

Only three pings

  • An agent is stuck (needs-human)
  • Personal PR merged
  • Company PR sent to supervisor
Basics

Phone layout

  • Big tap targets, main buttons at the bottom.
  • Lists, not wide tables. No sideways scrolling.
  • Stop asks "after this issue, or now?"
  • PR and issue links open the GitHub app.

11Risks and limits

Safety

No permission prompts

Agents run without asking, so run the loops in Docker, or use a tight command allowlist instead of bypass mode.

Quality

Codex reviewing Codex

When Codex built the PR, it may miss its own mistakes. Watch personal auto-merge for a while before you fully trust it.

Race

Two loops, one issue

Claiming by label is not atomic. Two loops could grab the same issue. Fix only if it actually happens.

Company

Stacked branches

An issue built on an unmerged blocker branch depends on the supervisor reviewing both. If the blocker PR changes, the stacked one needs a rebase.
